## 一、用户需求原文

> 将原来产品库里的导入数据和编码规则迁移到物料库，并重新规划编码规则内容，
> 物料大类一共有以下几类：成品、产成品、半成品、原材料、无用物料，说明一下：
> 1. 成品和产成品，现在有一种情况，一个物料号既属于成品，又属于产成品，正常来讲
>    成品由产成品组成，但实际上技术人员之前在录入资料时，因为有些成品只包含一个包装，
>    就省略了产成品这一层，所以就出现了一个物料既属于成品又属于产成品
> 2. 原材料包含多种内容，比如之前讲的售后物料其实也应该属于原材料
> 3. 无用物料包含类似模具、特采这一些比较特殊的内容
> 4. 之前是通过前缀来区分物料归属，实际上物料本身有分组编码这一项，但我又不放心
>    这个编码是否能够满足我要的分类

页面能力：

> 除了浏览、搜索等基础功能，需要为每一个物料做一个卡片，用于管理物料的属性，
> 比如可以放物料的图片等，同时在研发工具里的 bom 这个功能里有一个内容涉及到
> 物料的价格、供应商等内容，也可以迁移到这个位置

ERP 之外的属性范围：**先只要短名 + 分类**。

### 2.2 `TYPE_SEMI` / `TYPE_MATERIAL` 是死代码

`backend/database/models/product/erp_code_rules.py` 声明了这两个类型，但**全后端没有任何地方消费它们**
（grep 确认只有模型自身出现）。所以半成品和原材料目前只是"能配规则"，配了也没有任何表承接、
没有任何界面呈现——这正是用户说的"半成品、原材料并没有处理"。

### 2.3 按现有规则分类的实际分布

| 命中情况 | 条数 |
|---|---|
| 未命中任何规则 | **3,353**（41%） |
| material | 3,026 |
| semi | 873 |
| packaged | 352 |
| **finished + packaged（两者兼具）** | **276** |
| finished | 209 |

用户描述的"一个物料号既属于成品又属于产成品"**数据证实存在，276 条**。

所以这个多重归属机制**已经支持，不需要改造**。

## 三、关键结论：`group_code` 单独不足以决定大类

这是用户第 4 点疑虑的直接回答，**结论是不够用**。

67 个 `group_code` 中有 **9 个内部分类不一致**：

| 分组 | 条数 | 内部分布 |
|---|---|---|
| `1101` 成品_桌类 | 142 | 成品 126 / 成品+产成品 16 |
| `1108` 成品_成人桌 | 93 | 成品+产成品 50 / 未命中 36 / 成品 7 |
| `2001` 外贸成品_桌类 | 65 | 成品 50 / 成品+产成品 15 |
| `1102` 成品_椅类 | 52 | 成品+产成品 51 / 未命中 1 |
| `1104` 成品_附件类 | 124 | 未命中 111 / 产成品 13 |
| `3101` 贝视朗成品_灯类 | 31 | 成品+产成品 29 / 成品 1 / 产成品 1 |
| `14WD` 原材料_木器 | 596 | 原材料 595 / 未命中 1 |
| `14ME` 原材料_金属件 | 532 | 原材料 530 / 未命中 2 |
| `PCS` | 34 | 成品 23 / 未命中 9 / 产成品 2 |

区分靠的是**比分组更细的前缀**：

- `1101` 下：`1101LA` / `1101LD` / `1101LH` / `1101LS` 是产成品，`1101SG` 是成品
- `1108` 下有 10 条更细规则（`110802` / `1108KC` / `1108PW` / `1108SG` / `1108YJ` / `1108YY` / `1108ZJ`）
- `2001` 下：`2001JL` / `2001LD` / `2001LH` / `2001LS` / `2001LU` 均为产成品

`group_code` 表达不了这一层，所以**不能只靠分组编码**。

### 建议方案：分组编码定默认 + 前缀规则做例外覆盖

```
大类判定(code):
    1. 找出所有匹配 code 的「前缀例外规则」→ 命中则以它为准（可多标签）
    2. 否则按 code 的 group_code 查「分组默认大类」
    3. 都没有 → 未分类（页面上单独一个筛选项，便于收口）
```

理由：
- 58 / 67 个分组只需一行映射，维护成本低——满足用户"想用分组编码"的意图；
- 复杂度被限制在那 9 个分组上，用更细前缀覆盖，与现有规则的实际做法一致；
- 保留 `erp_code_rules` 表结构（`UNIQUE(prefix, type)` 已支持多标签），
  只需**新增一张分组默认表** `erp_group_category`，不需要推翻重做；
- 41% 未命中的数据会因为有了分组默认值而一次性被覆盖。

**成品/产成品保持多标签，不要做成单选 enum**——276 条兼具的数据是真实业务情况
（成品只含一个包装时省略了产成品层），强行互斥会丢信息。

## 四、模块归属迁移

| 内容 | 现在 | 迁移后 |
|---|---|---|
| ERP 导入数据（`import_product_raw`）管理界面 | 产品库 | **物料库** |
| 编码规则（`erp_code_rules`）管理界面 | 产品库 | **物料库** |
| 物料价格 / 供应商（`cost_material_price` / `cost_material_supplier`） | 研发工具 → BOM 成本 | **物料库**（BOM 计算继续读取，只是维护入口搬走） |
| 成品 / 产成品 / 标签 / 资料 / 生命周期 | 产品库 | 不动 |

注意：`cost_bom_node` 只有 130 条但 schema 比 `import_product_raw` 丰富得多
（`spec` 规格 / `category` 分类 / `purchase_type` / `material_type` / `weight_kg` / `area_m2`）。
**建议物料库的物料主数据表直接复用 / 扩展 `cost_bom_node`，而不是再建第三张物料表**——
否则 ERP 导入表、BOM 节点表、物料库表三份物料数据会长期互相打架。
这一点需要用户与 Codex 共同确认，是本方案最大的待决项。

## 五、页面设计（主页 → 业务数据 → 物料库）

- 左侧大类树：成品 / 产成品 / 半成品 / 原材料 / 无用物料 / 未分类，二级为分组
- 主区表格：编码、ERP 名称、短名、分组、大类标签、状态；支持编码/名称模糊搜索
- **物料卡片**（点击行展开或抽屉）：图片（OSS，参考 `ProductFinished.cover_image` 的既有实现）、
  短名、分类、规格、价格与供应商、备注
- 编码规则管理：分组默认大类表 + 前缀例外规则表，两个 tab
