## 🔴 P0 · `已停用` 不在状态词表中，两份真实文件全部被拒

```
变更前.xlsx → 第 74 行包含未知状态：已停用
变更后.xlsx → 第 38 行包含未知状态：已停用
```

`VALID_BOM_STATUSES` 目前只有 4 个值：

```python
{'已发布', '审核中', '通用变更审核中', '非通用变更审核中'}
```

真实文件里存在**第 5 个值 `已停用`**，两份各 5 行。

### 这 5 行是什么

| 编码 | 描述 | 版本 | 变更前层次 | 变更后层次 |
|---|---|---|---|---|
| `14ST01007` | 十字槽盘头尖尾自攻螺钉 | A01 | 2.4.15 / 2.4.26.3 | 3.1.4 / 3.1.15.11 |
| `14ST08001` | CPE软骨自封袋 | A01 | 2.6.5 | 3.3.11 |
| `14ST05032` | 调节地脚 | A01 | 3.2.19 / 3.5.14 | 4.3.7 / 4.5.13 |

全部是**标准件**，**前后两份文件里都存在、编码与版本完全相同**，
只是层次号因插入新物料而整体位移。即：**它们在本次变更中没有变化**，
只是这些物料本身在 ERP 里已被停用，但仍留在 BOM 中。

### ✅ 用户已确认语义（2026-08-06）

> 已停用和已发布是同一个状态，实际都为「已发布」状态。

即 **`已停用` 与 `已发布` 完全等价**，只是同一状态的两种写法。

### 修法：不能只加进词表，必须处处等价

新增一个"已发布语义"集合，**所有原本判断 `== STATUS_PUBLISHED` 的地方都改用它**：

```python
STATUS_DISABLED = '已停用'
# 已停用与已发布是同一状态的两种写法，语义完全等价
PUBLISHED_STATUSES = {STATUS_PUBLISHED, STATUS_DISABLED}
VALID_BOM_STATUSES = PUBLISHED_STATUSES | {
    STATUS_NEW, STATUS_COMMON_CHANGE, STATUS_NON_COMMON_CHANGE,
}
```

#### 🔴 关键的连带点：`validate_bom` 的 after 校验会被静默削弱

`change_documents.py:266`：

```python
if role == 'after':
    if all(s == STATUS_PUBLISHED for s in statuses):
        return '变更审核中文件的状态列全部为「已发布」，该文件应包含处于审核中状态的物料'
```

如果只把 `已停用` 加进 `VALID_BOM_STATUSES` 而**不改这一行**，后果是：

> 任何含 `已停用` 行的 BOM，`all(s == '已发布')` 必为 `False`，
> 于是**即使整份文件里没有任何审核中的行，这条校验也会通过** ——
> 用户拿两份完全相同的文件当变更前后，系统不会拦，只会产出一张空变更单。

这是**静默削弱校验**，比报错难发现得多。本样本 226 行里就有 5 行 `已停用`，
也就是说这条校验对真实文件**立刻失效**。

必须改成：

```python
if all(s in PUBLISHED_STATUSES for s in statuses):
```

错误文案建议同步改为「…状态列全部为「已发布」（含「已停用」）…」，
否则用户看到报错会去找哪一行不是「已发布」而困惑。

#### 其他位置无需改动

- `_derive_new_drawing` / `compare_bom` 用的是 `status in CHANGE_STATUSES` 与
  `status == STATUS_NEW` 的**正向判断**，`已停用` 自然落到"非变更"分支、
  返回原图号，行为已正确；
- 解析阶段只做词表校验，加进词表即可。

### 顺带仍建议

未知状态报错时**列出该文件出现的全部未知值**（现有 `unknown` 已是 sorted 集合，
`validate_bom` 里做对了；但 `_parse_bom:316` 是逐行遇到即 raise 第一个）。
建议 `_parse_bom` 也先收集完再一次性报，避免用户反复试错——
`已停用` 这次就是这么被发现的：报了第 74 行，修完可能还有别的值在后面。

### 2. 层次号会整体位移 —— 而 `compare_bom` 的设计已经能扛

插入新物料（层次 2）导致其后所有层次号位移：变更前的 `2.x` → 变更后的 `3.x`，
`3.x` → `4.x`。两份文件的层次交集极小、差异达数百行。

**幸运的是这不构成问题**：`compare_bom` 的匹配键是 `(parent_code, code)`
而非 `(level, code)`，代码注释里也写明了这个设计意图。所以层次位移**不会**
造成假增删。

> 这也说明我此前几轮用「层次」对账是可行的（那两份是同一棵树），
> 但真实变更场景下**不能**按层次匹配 —— 好在实现本来就没这么做。

### 3. `validate_bom` 的角色调用是安全的

`变更前.xlsx` 里也有 1 行 `非通用变更审核中`（层次 1 顶层 `1201TSSJ01` 探索家_书架，
前后两份文件相同）。如果变更前文件按 `role='before'` 校验（要求全部「已发布」），
它会被拒。

实际调用（`routes/rd/__init__.py:139,142`）是：

```python
err = validate_bom(before_path, role='any')    # 只校验列名，不校验状态
err = validate_bom(after_path,  role='after')  # 要求不能全是「已发布」
```

**变更前用的是 `role='any'`**，所以不会被拒 —— 这个设计正确，无需改动。
