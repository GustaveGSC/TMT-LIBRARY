# 物料库·研发 BOM 后端评估报告

评估日期：2026-09-27  
评估范围：提交 `608d816` 的后端模型、迁移、导入/查询服务、路由和测试。  
执行边界：只读代码审查；未修改代码、未执行迁移、未连接生产数据库、未写入任何业务数据。

## 1. 结论摘要

当前实现的总体架构方向正确：研发 BOM 与成本快照 BOM 分表、按“研发编码+研发版本”保存单层结构、按需逐层展开，能够表达同一 ERP 物料对应多个研发版本，也没有明显 N+1 查询。对已经验证过的、层次列为文本且数量合法的 PDM 样例，可以继续保留上线状态。

但在生产库仍为 0 条 BOM、尚未正式导入的窗口期，建议先补完一批导入正确性护栏再开放常规使用。没有发现会绕过权限或立即损坏现有业务表的 P0 安全漏洞；以下两项按“首次正式导入前必须修”定为 P0：

1. 数量为空或非法时被静默改成 `1`，零数、负数及超出 `NUMERIC(14,4)` 的值也未拒绝，可能把错误用量作为正式 BOM 保存。
2. 层次结构没有完整校验：数字单元格会丢失 `1.10` 的文本语义，重复层次、缺父级、乱序行会被覆盖或静默跳过，可能生成结构错误但接口仍返回成功。

另有三个高优先级 P1：统一编码/版本大小写避免 MySQL 唯一约束 500；同一父件重复展开时校验内容一致而不是无提示取第一次；对 Excel 字段长度、状态值和重复子件冲突做明确校验。

建议暂时维持“`.` 子零件和 `14ST10*` 照存、`erp_code=NULL`”的行为。它们是研发结构的一部分，直接跳过会丢失 BOM 信息；“把数量并到上级”在量纲上不成立。可后续增加来源/未匹配原因展示，但不应在导入层删除。

## 2. R1–R11 逐条评估

### R1：ERP 编码关联在导入时固化 — P1，成立

证据：`MaterialBomService.import_file()` 只在导入时调用 `_erp_resolver()` 并写入 `MaterialBom.erp_code` / `MaterialBomLine.erp_code`（`material_bom.py:181-215`）；ERP 导入 `ImportProductService.import_rows()` 只失效物料分类缓存（`import_raw.py:49-61`），没有重算 BOM 关联。

建议保留“持久化 `erp_code`”设计，不改成每次读取时动态匹配。读时匹配会使列表标记、反查和树展示都依赖字符串候选计算，削弱现有索引并扩大每次请求的查询复杂度。

具体改法：

- 在 `MaterialBomService` 新增 `relink_unmatched_erp_codes()`，只读取两个表中 `erp_code IS NULL` 的去重 `(code, version)`，复用规范化后的 resolver，再批量更新能够新匹配的表头和明细。
- 在 `ImportProductService.import_rows()` 完成 ERP UPSERT 后调用该方法；它只处理未匹配项，不扫描/重写全部 BOM。
- 返回或记录 `bom_headers_relinked`、`bom_lines_relinked`，便于验证和观测。
- 不建议自动清空已经匹配的 `erp_code`。当前 ERP 导入是 UPSERT、不删除旧编码；如果以后引入删除语义，再单独设计解绑审计。

数据量成本：查询规模与“尚未匹配的 BOM 编码数”相关，而不是 8,000 多条 ERP 物料全量笛卡尔匹配；候选继续按 1000 个分批查询即可。

### R2：旧的下级 BOM 不会被清理 — P2，现状语义合理

证据：`build_single_level_boms()` 把每个有下级的物料视为独立 BOM；`import_file()` 只覆盖本次文件中存在的 `(code, version)`。父件不再引用某半成品，不代表该半成品自己的结构失效，它仍可能被其他产品引用。

因此不要在父件重导时级联删除下级 BOM，也不要因为本次文件把某节点表现为叶子就自动删除它的既有定义。建议增强可见性：

- 列表查询增加 `reference_count` / `is_orphan`（没有被任何 `material_bom_line(code,version)` 引用且自身不是本次已知根节点时只能称“可能孤立”，因为当前没有持久化根集合）。
- 更稳妥的做法是在导入批次中持久化 root 标记或导入批次表，再区分“顶层 BOM”和“真正孤儿”；在没有这一信息前只显示“无上级引用”，不要自动清理。

### R3：数字层次导致 `1.10` 变成 `1.1` — P0，成立且会静默破坏结构

证据：共享 `_level_str()` 对 float 直接 `str(v)`（`change_documents.py:126-134`）；Excel 数字 `1.10` 在读取时已经是 `1.1`，无法从值本身恢复。`build_single_level_boms()` 又以层次字符串作为字典键（`material_bom.py:98-107`），重复值会覆盖先前行，缺父级的行直接 `continue`。

建议不要尝试用 `number_format` 猜回层次。`1.10` 和 `1.1` 在 Excel 数值层已经不可区分，猜测会制造另一类错误。具体改法：

- `parse_bom_rows()` 要求“层次”单元格必须是字符串；整数根层（如数值 `1`）是否兼容可单独允许，但任何非整数 float 直接返回带 Excel 行号的明确错误：“层次列必须设置为文本格式”。
- 解析后新增结构校验：层次非空、格式符合 `数字(.数字)*`、同一个 root 段内层次不重复、非根节点必须已有直接父级、父级必须出现在子级之前。
- 禁止 `build_single_level_boms()` 对缺父级行静默跳过；改为在进入构建前一次性汇总全部结构错误。

### R4：编码大小写与 MySQL 排序规则 — P1，成立

证据：`material_bom(code,version)` 使用数据库默认排序规则，生产 MySQL 的 ai_ci 唯一约束不区分大小写；但 `_erp_resolver()` 的 `existing` 是 Python 大小写敏感集合（`material_bom.py:151-166`），导入查到 `A01` 后使用 `a01` 检查会失败。查询旧 BOM 时 MySQL 可能返回记录，但 `existing` 字典的 Python key 与输入 key 不同，随后会走新增并在唯一约束处报 1062。

建议在所有持久化和查询前统一规范化，而不是改成二进制排序规则：

- 新增公共 `_normalize_code()` / `_normalize_version()`：去首尾空格并 `upper()`；对 PDM 和 ERP 两个解析分支都应用。
- `_VERSION_LETTERS_RE` 只接收规范化后的版本。
- 导入前检查规范化后是否发生键碰撞，并给出原始行号，不能留到数据库报唯一约束错误。
- 迁移前生产表为 0 行，无历史回填成本；后续如果已有数据再改必须先做碰撞审计。

### R5：同步导入与内存/worker 风险 — P1，成立但当前样例可控

证据：路由同步调用 `import_file()`；`parse_bom_rows()` 使用 `load_workbook(read_only=False)` 并按单元格随机读取（`material_bom.py:37-89`）。上传层限制压缩包/解压体积和最大行数，但 20MB xlsx、100MB 解压上限仍可能明显占用 1.7GB 服务器唯一 worker。

建议第一批先做低成本限制，不急于引入后台任务：

- 切换 `read_only=True`；`_bom_columns()` 对只读 worksheet 仍可读取首行，但解析应改为 `iter_rows(values_only=False)` 单次流式遍历，保留 `_numeric_code_text(cell)` 所需的 number format。
- 为研发 BOM 单独设置更窄的行数/BOM 数量上限，例如先按真实文件规模制定（226 行样例可从 5,000 行起），超限明确拒绝。
- 记录解析耗时、行数、生成 BOM 数和明细数。只有真实文件接近秒级/内存门槛时，再迁移到持久化后台任务；几百行不值得现在引入任务复杂度。

### R6：直接上级按 ERP 编码、继续向上按研发版本 — P2，口径正确

物料卡片回答的是“这个 ERP 物料被哪些研发结构使用”。同一 ERP 物料映射到 A01/A02 时，合并这些研发版本的引用是符合该问题口径的；继续向上必须按 `(code,version)`，否则会把不同研发版本的结构串错。

当前结果按 BOM id 去重，能保留不同上级研发版本；没有发现漏算逻辑。建议只补测试：同一 ERP 码映射两个研发版本、分别被两个不同顶层引用，断言两个顶层都返回且不重复。

### R7：`.` 子零件和 `14ST10*` 跳过规则 — 待产品选择；技术建议为“照存”

详见第 4 节。结论：ECR 比对跳过某类行，不代表研发 BOM 结构库也应跳过；两个功能的业务目的不同。

### R8：复用 ECR 私有函数 — P1，成立

证据：`material_bom.py:21-23` 直接导入 `_bom_columns/_level_str/_numeric_code_text/_category_name`。这些以下划线命名，且 ECR 对状态、编码跳过和新物料规则与物料 BOM 已经不同。

建议抽取纯 Excel 基础能力到 `backend/services/common/bom_excel.py`（或 `services/rd/bom_excel.py`，但不要反向依赖具体 ECR 服务）：

- 共享：表头识别、编码单元格转文本、分类名清洗、严格层次解析。
- 各业务自己保留：状态口径、跳过规则、品名/规格拼接、版本推算。
- `change_documents.py` 与 `material_bom.py` 同时改为从公共模块导入，并保留现有行为回归测试。

### R9：查询量和 MySQL 索引 — P2，静态设计合理；仍缺真实 EXPLAIN

静态证据：

- `material_bom` 有唯一索引 `(code,version)`；树展开的 `tuple_(code,version) IN (...)` 与该索引前缀完全一致。
- `material_bom_line` 有复合索引 `(code,version)`；向上反查使用同形状 tuple IN。
- `erp_code` 两表均有单列索引，直接上级、版本列表、当前页 `has_bom` 均可利用。
- `tree()` 是每层两条查询、最终 ERP 信息一条；`for_material()` 是常数查询加每层两条，不存在逐节点 lazy load。

本次遵守“不接触生产数据”，没有执行生产 EXPLAIN，因此不能把“实际命中索引”写成已验证事实。正式导入少量数据后应只读执行：

```sql
EXPLAIN ANALYZE SELECT * FROM material_bom
 WHERE (code, version) IN (('A','A01'),('B','A02'));
EXPLAIN ANALYZE SELECT * FROM material_bom_line
 WHERE (code, version) IN (('A','A01'),('B','A02'));
EXPLAIN ANALYZE SELECT DISTINCT erp_code FROM material_bom
 WHERE erp_code IN ('1101DL01-A','1303001-A01');
```

门槛：前两条应显示复合索引访问而非全表扫描；行数增长后若 MySQL 对 row-constructor IN 选择不稳定，可改为临时候选表/JOIN，但当前规模无需预优化。

### R10：测试只覆盖 SQLite、缺 ERP 格式 — P1，成立

必须补：

- 真实 MySQL 集成测试：大小写输入与 ai_ci 唯一约束、`tuple IN` 查询结果、`Numeric(14,4, asdecimal=False)` 返回类型、`ON DELETE CASCADE`。
- ERP 格式解析测试：带/不带版本、编码本体含 `-`、空图号、文本层次、数量小数。
- 数字层次拒绝：`1.1` 数值单元格明确失败；文本 `1.10` 与 `1.1` 能独立存在。
- 结构错误：重复层次、缺父级、子级先于父级、跨级跳跃均失败且包含 Excel 行号。
- 大小写：`a01` 被规范化为 `A01`，二次导入更新而非 500。
- 重复展开：完全一致允许去重；内容/数量/单位不同必须失败并指出两个展开位置。
- 非法数量、零/负数、四位以上小数、超范围、字段超长均明确失败，不写库。
- ERP 重导后原先 unmatched 的表头和明细能自动 relink。
- R6 的多研发版本反查用例。

### R11：事务与 rollback — P2，基本成立但建议显式收口

导入的 DELETE、UPDATE/INSERT 和最终 commit 在同一 session 中；中途异常时 Flask-SQLAlchemy 请求 teardown 的 `session.remove()` 会回滚未提交事务，现有路由也不会在捕获异常后继续复用 session，因此当前不会留下半写数据。

仍建议 `import_file()` 在写入阶段用明确的 `try/except`：异常时 `db.session.rollback()` 后重新抛出，理由是 service 未来可能被脚本/测试/后台任务直接调用，不一定拥有请求 teardown。批量 DELETE 的 `synchronize_session=False` 在当前代码里安全，因为旧 line 对象没有被预加载并继续使用。

## 3. 新发现的问题

### N1：非法数量静默变成 1 — P0

`parse_bom_rows()` 在 `float()` 失败时直接 `qty=1.0`（`material_bom.py:78-81`）。这会把空值、文本错误和公式异常变成合法业务数据，无法从导入结果识别。

改法：收集行级错误并整体拒绝；数量必须是有限数、`>0`、最多 4 位小数且能落入 `NUMERIC(14,4)`。如果业务允许 0 数量，必须由用户单独确认，不能靠默认值猜测。

### N2：重复展开内容不一致时静默采用第一次 — P1

`build_single_level_boms()` 用 `owner` 跳过同一 `(code,version)` 的后续展开（`material_bom.py:108-112`），但没有比较后续展开是否真的相同。文件内部若两处展开不同，结果取决于行顺序。

改法：为每次展开构造规范化签名（子件 code/version、数量、单位，按稳定顺序），同一父件重复出现时签名一致才去重；不一致则拒绝导入并列出两个父层次和差异子件。

### N3：重复子件合并忽略单位/名称等冲突 — P1

同一父件下相同 `(code,version)` 直接相加数量，后出现行的单位、名称、规格、分类全部被忽略（`material_bom.py:113-118`）。若一行 PCS、一行 SET，会产生无意义总数。

改法：合并前要求单位一致；名称/规格/分类若两个非空值不一致则报错。只允许完全同语义的重复行相加。

### N4：状态列被要求存在但完全未读取 — P1（需要产品确认口径）

`_bom_columns()` 要求“状态”列，但 `parse_bom_rows()` 不使用它。于是“审核中”“已停用”或未来未知状态都会进入正式研发 BOM。

建议明确物料 BOM 的状态口径：如果它表示当前已发布结构，则只接受 `PUBLISHED_STATUSES`；如果需要查看审核中结构，则表头必须保存 `status` 并在列表/版本上标识，不能与已发布结构无差别覆盖。当前产品描述更接近“正式物料 BOM”，建议第一批只收“已发布/已停用是否保留由用户确认”，未知状态必须拒绝。

### N5：字段长度没有导入前校验 — P1

模型限制 code 64、version 16、name 255、spec 512、category 64、unit 16；解析器未校验。MySQL 严格模式会在 flush 时 1406 并返回泛化 500，非严格模式还有静默截断风险。

改法：解析阶段按字段逐项验证长度并带 Excel 行号报错；不要依赖数据库异常。

### N6：根节点和导入批次没有持久化 — P2

返回值里的 `roots` 只在本次响应存在，数据库无法区分顶层 BOM 与暂时无引用的半成品 BOM。这限制了“孤儿提示”和按一次文件整体审计/回滚。

短期不必迁移；若后续确实需要孤儿治理或整批撤销，可新增 `material_bom_import` 批次表和 root 关联。不要仅凭无上级引用自动删除。

### N7：导入异常只返回通用错误，缺少可操作信息 — P2

路由对非 `UploadValidationError` 统一返回“BOM 导入失败”。在补齐输入校验后，大部分用户错误应转换为带行号的 `UploadValidationError`；真正数据库/程序异常继续记录错误编号，避免暴露内部信息。

## 4. R7 跳过规则方案对比

| 方案 | 数据完整性 | 查询/展示 | 数量处理 | 风险与适用场景 |
|---|---|---|---|---|
| 照存，`erp_code=NULL`（推荐） | 最完整，保留研发原始结构 | 树中正常显示，但标“未匹配/非 ERP”；不进入 ERP 物料卡片反查 | 保留原数量 | 最安全、可逆；会增加 unmatched 数量，但这是事实而非错误。适合研发结构库 |
| 直接跳过 | 永久丢失这些节点 | 树更干净，与 ECR 当前行为表面一致 | 叶子数量直接丢失 | 仅当业务明确这些行是纯 CAD 噪音且永远不参与装配/采购时可选；`14ST10*` 标准件通常不应这样处理 |
| 跳过并把数量并到上级 | 结构和语义都被改变 | 上级看似保留“总量” | **不可直接相加**；不同物料/单位数量没有共同量纲 | 不建议。若被跳过节点只是虚拟中间层，正确做法是把其子件提升一级并将数量相乘，而不是把自身数量加给父件；对叶子仍无可合并对象 |

建议决策：本期维持照存。可按规则给 unmatched 增加派生原因：`dot_subpart`、`standard_14st10`、`erp_missing`，前两类不计入“异常匹配失败”数量，但仍保存和展示。该增强可只在响应/序列化阶段推导，不一定需要迁移。

## 5. 成本 BOM 是否打通

不建议复用或合并 `cost_bom_node/cost_bom_line`：

- `cost_bom_line` 属于具体 `cost_snapshot_sku`，表达某次成本导入快照，不是唯一的当前研发结构。
- `cost_bom_node.code` 去版本且唯一，`code_with_version` 只是附加字段；研发 BOM 必须区分 A01/A02，强行复用会覆盖版本语义。
- 成本行包含 unit_price/total_price、外购半成品等计算语义；研发 BOM 包含源文件、研发分类和版本结构，生命周期不同。

可以做单向、只读关联：在研发 BOM 树展示价格时通过 `erp_code`/现有成本节点解析服务批量取最新价；采购/成本导入仍只更新成本表，不反向覆盖研发结构。不要增加两套 BOM 行之间的外键。

## 6. DELETE 硬删除评估

当前硬删除不会违反数据库外键，因为其他 BOM 通过 `(code,version)` 松耦合引用；但它会让所有父 BOM 中相同子件从“可展开”立即退化为叶子，且没有审计记录或恢复能力。定为 P1。

建议两阶段：

1. 短期：删除前查询 `material_bom_line(code,version)` 引用数；有引用时返回冲突信息，要求显式 `force=true` 二次确认。响应包含引用父件列表/数量。无引用仍可硬删。
2. 若实际存在误删恢复需求，再迁移增加 `is_active/deleted_at/deleted_by` 做软删除；所有树/列表/反查只取 active，重新导入同版本自动恢复。生产目前 0 条，若决定软删除现在改迁移成本最低。

不建议把“无引用”自动等同“可清理”，因为顶层成品天然无上级引用。

## 7. 建议修复分批

### 第 0 批：首次正式导入前的正确性门禁（P0/P1，无迁移）

文件：`services/product/material_bom.py`、抽出的公共 `services/common/bom_excel.py`、`tests/test_material_bom.py`。

- 严格校验文本层次、父级顺序、重复层次。
- 严格校验数量、字段长度、状态。
- code/version 统一大写规范化，并检测规范化碰撞。
- 重复父件展开做内容等价校验；重复子件仅在单位和元数据一致时合并。
- 显式 rollback。
- 补 PDM/ERP 两种格式及错误行号测试。

迁移：不需要。生产仍为 0 条时最适合完成。

### 第 1 批：ERP 重导后的自动补关联（P1，无迁移）

文件：`services/product/material_bom.py`、`services/product/import_raw.py`、相关测试。

- 新增只处理 `erp_code IS NULL` 的 relink。
- ERP UPSERT 后调用并返回统计。
- 测试原先未匹配编码在 ERP 新增后，表头/明细均补上关联，已匹配项不被重写。

迁移：不需要。

### 第 2 批：删除保护与孤立可见性（P1/P2，是否迁移由产品选择）

文件：service、route、API 文档、前端确认交互。

- 最小方案：引用检查 + force 二次确认，无迁移。
- 完整方案：软删除字段与导入自动恢复，需要 Alembic 迁移。
- 增加“无上级引用”统计，但不要自动删除。

### 第 3 批：性能与 MySQL 门禁（P2，无业务迁移）

- 使用真实 MySQL 测试上述 collation、tuple IN、Numeric 和 cascade 行为。
- 第一份正式数据导入后执行只读 `EXPLAIN ANALYZE`，记录 rows/actual time/index。
- 将解析改为 read-only 流式，并基于真实最大文件设研发 BOM 专用上限。
- 若真实导入耗时仍明显占用唯一 worker，再设计持久化后台任务；不要提前复杂化。

## 8. 最终建议

保持现有双表单层存储架构，不与成本 BOM 合表，不自动删除下级 BOM，`.` 和 `14ST10*` 暂时照存。首次生产正式导入前，先完成第 0 批；之后用用户提供的真实文件做“解析预览 → 行数/根/未匹配分类核对 → 导入 → 树与反查抽样”的门禁。R1 自动补关联可以紧随其后，不阻塞当前已匹配的首份文件，但应在下一次 ERP 重导前完成。
