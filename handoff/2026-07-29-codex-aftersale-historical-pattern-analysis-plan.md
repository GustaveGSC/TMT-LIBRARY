# 售后历史工单补全：规律分析第 0 阶段（只读）

日期：2026-07-29  
状态：已完成代码侧梳理；**尚未读取生产历史数据，也未写入任何工单**。

## 目标与边界

目标是使用 2026 年人工确认的工单，向 2024/2025 年仍为 `pending` 的工单提供可解释的补全建议。

本阶段只产生统计报告和候选清单，禁止：

- 调用 `POST /api/aftersale/cases` 或直接更新 `aftersale_case` / `aftersale_case_reason`；
- 把模型/关键词推荐直接当作人工确认；
- 为了分析启动完整 Flask 应用。`create_app()` 会处理遗留任务状态，不是只读入口。

生产分析须使用单独数据库连接，并在连接建立后立即执行：

```sql
SET SESSION TRANSACTION READ ONLY;
```

## 已确认的数据规律来源

一张已确认工单可提供下列监督信号：

| 信号 | 来源 | 适合推断 | 风险 |
|---|---|---|---|
| 原因标签 | `aftersale_case_reason.reason_id` / `reason_category_id` | 故障原因、一级分类 | 一个订单可有多条原因，不能把整单备注无条件归为其中任一条 |
| 发货物料简称 | `aftersale_case_reason.shipping_alias_id` | 物料/部件归属 | 同一物料词可能对应多个简称 |
| 型号 | `aftersale_case_reason.model_id` | 产品型号 | 旧订单的产品编码可能与 2026 不完全重合 |
| 备注 | `aftersale_case.seller_remark`、`buyer_remark` | 原因候选 | 买家留言应从商家备注中剔除，避免把需求文本当故障文本 |
| 订单物料 | `aftersale_case.products` | 简称/型号候选 | 商品可能多件、多型号 |

现有 `auto_match()` 是交互期的推荐器，不应直接用于历史批处理：它的历史语义缓存最多只取最近 150 条已确认工单，且会受到进程缓存、当前词典和语义模型可用性的影响。历史补全必须改用一次性、可复跑的离线分析结果。

## 建议的规律层级

1. **确定性规则（可作为自动填充候选）**
   - 规范化后完全相同的有效商家备注，在已确认单中只对应一个 `reason_id`；
   - 同一物料编码/清洗后物料 token 在已确认单中只对应一个 `shipping_alias_id`；
   - 上述两项同时命中，且与该原因、型号的历史共现一致。

2. **高置信统计规则（需抽样复核后才可批量应用）**
   - 同一证据键至少出现 5 次；
   - 第一候选占该证据键样本至少 95%，且第一、第二候选计数差至少 4；
   - 证据键为 `备注短语 + 物料简称` 时优先于只有备注或只有物料的规则。

3. **人工队列，不自动补全**
   - 多原因订单无法把单条备注切分到具体原因；
   - 候选并列、样本数少、备注为空、或涉及自定义原因；
   - 仅有语义相似度而没有可解释的文本/物料证据。

## 生产只读分析应输出的四份结果

1. **规模与可训练性**：2024、2025、2026 按 `pending/confirmed/ignored` 分组的工单数；2026 已确认单中原因、型号、简称、备注的非空覆盖率和多原因比例。
2. **原因规律表**：`规范化有效备注 -> reason_id` 的支持数、纯度、第二候选、示例订单；另输出 `备注 + 物料 token -> reason_id` 的同类指标。
3. **物料规律表**：`物料 code/token -> shipping_alias_id/model_id` 的支持数、纯度、示例订单。
4. **待补全候选清单（只读导出）**：每个 2024/2025 pending 订单列出推荐原因/简称/型号、命中规则、支持数、置信度等级、冲突原因；不含任何确认动作。

## 验收门槛

在讨论任何批量写入前，必须：

1. 将 2026 已确认工单按处理时间做时间切分验证（早期训练、后期验证），分别报告原因、简称、型号的覆盖率与准确率；
2. 人工盲审至少 50 条“高置信”候选和 30 条“中置信”候选；
3. 高置信候选达到人工准确率 >= 98% 才讨论自动草稿/批量确认，未达标则只作为界面建议；
4. 任何实际写入先在可回滚的事务/备份方案下按小批量执行，保留每条命中规则与版本号，支持逐批撤销。
