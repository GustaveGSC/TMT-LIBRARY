# 物料高级筛选表达式后端完成，交接 Claude

日期：2026-08-03  
状态：代码完成、本地验证通过、**未部署**

## 决策与实现

- `match_mode` 现为 `like|expr`；默认 like，非法模式返回 400。
- 已移除无前端调用方的 regex 模式及全部 MySQL ICU/DBAPIError 特殊处理。
- expr 使用独立递归下降解析器生成 AST，再生成 SQLAlchemy `AND/OR/NOT + LIKE` 条件，
  不转换成正则。
- 支持：
  - `A & B`
  - `A | B`
  - `!A`
  - `(A | B) & !C`
  - `"(V1.1)"` 字面量
- `&` 优先于 `|`；操作数首尾空格移除，双引号内部按字面量保留。

## 安全与错误

- 嵌套深度上限 10，AST 节点上限 50；超限返回“表达式过于复杂”。
- 明确区分并返回：括号不匹配、引号不匹配、缺少操作数、操作数不能为空。
- 表达式只生成 ORM 条件，不拼接 SQL 字符串。
- like 和 expr 的每个操作数都转义 `\\`、`%`、`_`，并显式使用 `ESCAPE '\\'`。
  因此 `MJ120_A` 不再错误匹配 `MJ120XA`。
- 旧 keyword 联合搜索保持原行为，不受 match_mode 影响。

## 性能

- 每个操作数生成一个 LIKE 条件；不增加额外 SQL。
- 普通列表仍为缓存热态三条 SELECT：COUNT、分页、当页人工属性。
- 大类筛选仍先在 SQL 应用表达式，再做轻量字段的大类判定。

## 验证

- `桌腿 & !红色`、`(桌腿 | 桌面) & !红色` 结果正确。
- `"(V1.1)"` 能按字面量匹配半角括号内容。
- 默认 like 与单操作数 expr 等价。
- `_` 通配符转义回归通过。
- 八种错误输入和两个复杂度上限均有测试。
- 路由错误通过真实 Cookie JWT 返回 400。
- 全量 pytest、compileall、diff check 通过。
