## 2. 模块关系

```text
ERP/财务文件
  └─ 发货导入服务
      ├─ shipping_record / return_record
      ├─ 操作人分类、仓库排除、财务客户映射
      └─ 订单解析
          ├─ 产品库成品/产成品/等效件
          └─ shipping_order_finished
              ├─ 发货图表
              ├─ 产品生命周期与产品详情月度图
              └─ 售后图表的销量分母

shipping_record + 售后操作人分类
  └─ 售后待处理队列
      └─ aftersale_case / aftersale_case_reason
          ├─ 产品型号
          ├─ 原因库、简称库、关键词学习
          ├─ 售后图表/导出
          └─ 产品详情售后月度图
```

这说明：

- 发货模块同时承担“源数据接入”和“派生订单分析”；
- 售后不是独立数据源，而是消费发货原始记录，并再引用产品主数据；
- 当前“数据管理”没有自己的后端领域，它只是把发货域、产品域的写操作集中到一个页面。

## 3. 发货模块独立发现

### P0/P1：仓库过滤写接口被错误降为查看权限

`backend/routes/shipping/__init__.py`：

```python
_VIEW_POST = ('/chart-data', '/chart-options', '/warehouses/filter')
```

`make_blueprint_guard()` 对 `view_post_paths` 只校验 `shipping:view`，不校验
`shipping:edit`。因此仅有查看权限的账号可以调用：

```http
POST /api/shipping/warehouses/filter
```

修改仓库排除规则。该配置会改变后续财务销退导入口径，不是查询操作。

建议：

- 立即从 `_VIEW_POST` 删除 `/warehouses/filter`；
- 补真实 Cookie JWT 权限测试：viewer=403、editor=200；
- 检查 `_VIEW_POST` 中无效的 `/chart-options` 项并清理，避免白名单继续靠手工维护。

### P1：所有重型写任务都可并发启动

以下任务没有互斥、租约或准入控制：

- 发货导入；
- 财务导入；
- 全量 `resolve-all`；
- 增量 `resolve`。

同一用户双击、多个用户操作或断线后重复提交，都可以创建多个后台线程。后果不只是资源竞争：

- 多个 Excel 解析和大事务会同时占用有限内存、CPU、数据库连接；
- 导入与全量重算交错时，派生表的“先删后插”可能覆盖另一任务结果；
- 两个 resolve 对同一订单并发写入时结果取决于执行顺序；
- 单 worker 场景并不等于只有一个后台线程。

建议用数据库状态建立“发货数据变更任务租约”，同一时刻只允许一个
`import_shipping/import_finance/resolve_all/resolve_stale` 运行。冲突返回标准 409，并返回当前任务
ID，前端跳转查看进度。任务创建与抢占租约应原子化，不能只看进程内字典。

### P1：取消在解析和订单解析阶段不完整

当前 `cancel_check` 只在部分插入进度回调中检查；`_resolve_orders()` 没有取消参数。
用户在解析大文件或 resolve 阶段点击取消，界面显示“已发送中止信号”，任务仍会继续。

建议：

- 把取消令牌传到解析、批量写入和 `_resolve_orders`；
- 每个安全批次边界检查，而不是每行检查；
- 明确“取消后整个导入事务回滚”，全量重算则需要先写临时结果或明确其可回滚边界；
- 测试在 parsing/inserting/resolving 三个阶段取消。

### P1：派生数据与图表缓存失效仍靠调用方记忆

Claude 指出的产品规则、标签分类删除、标签删除遗漏成立。独立复核进一步确认根因是：

- `_invalidate_chart_options_cache()` 位于仓储文件，但由 route/service 零散导入；
- 产品、标签、ERP 规则、发货导入和重算均可能改变结果；
- 没有“产品分析维度已改变”或“发货派生数据已改变”的统一事件。

建议不要继续逐个补 import，而是先建立两个明确失效入口：

- `invalidate_product_analysis_dimensions()`
- `invalidate_shipping_derived_data()`

所有相关服务级事务成功后调用；禁止在事务提交前清缓存。

### P1/P2：订单解析存在不确定 tie-break

`_resolve_orders` 的贪心匹配依赖查询返回的产品/组合顺序。当多个候选拥有相同匹配规模时，
没有稳定排序和业务 tie-break，MySQL 返回顺序变化可能让同一订单解析成不同产品。

建议先采集并审计冲突样本，再确定稳定规则，例如：

1. 精确物料集合优先；
2. 匹配件数；
3. 非等效替换数量；
4. 产品状态/生命周期；
5. 最后以产品编码稳定排序。

发生同分冲突应记录可查询的诊断信息，不能静默任选。

### P2：路由层仍混有配置业务和 ORM

`/equivalents` 三个端点直接在 route 中导入模型、查询、校验并提交，不符合该模块其他部分的
route → service → repository 边界。拆分成本低，可与等效件功能归属调整一起做。

### P2：输入和结果集合仍需边界

- 售后/发货列表已有部分分页限制，但并非所有跨模块集合一致；
- 图表细分会按国家逐个发请求，属于前端 N 次请求而非后端 N+1；
- 财务客户映射的批量选择受单页最多 500 条限制，超限后需要明确提示或改成服务端选择语义。

### 单 worker + CPU 任务结论修正

Claude 建议在循环中加 `time.sleep(0)`。这只能作为经基准验证后的微小调度优化，不是可靠的架构修复：

- CPython 会周期性切换 GIL，并不是 Python 循环可以连续 1800 秒完全不让出；
- `sleep(0)` 不能解决总 CPU、内存峰值、并发任务或派生数据竞态；
- 真正优先项是任务准入控制、分批边界、指标监控和超时压测。

建议先在生产同规格环境测量最大允许文件的解析时长、RSS、心跳和 API 延迟，再决定是否增加显式
yield；不要把 `sleep(0)` 当作“已解决看门狗风险”。

## 4. 售后模块独立发现

### P1：重复确认不是幂等操作，会累计污染学习数据

`confirm_case()` 声明“创建或更新工单”，存在工单时会删除旧原因后重建，但没有像
`update_case()` 那样先撤销旧原因统计。

重复提交同一订单会再次：

- 增加 `AftersaleReason.use_count`；
- 增加原因—简称亲和度；
- 积累关键词候选和自动学习数据。

数据库对订单号的唯一约束只防止重复工单行，无法防止这些计数重复。网络重试、双击或客户端超时后
重提都会触发。

建议：

- 明确 `POST /cases` 是一次性确认还是 upsert；
- 推荐已有工单时走同一套“撤销旧贡献 → 写新内容 → 重新贡献”的事务；
- 或对已确认工单返回 409，要求使用 PUT；
- 增加同一请求重复两次后所有计数不变的幂等测试。

### P1：售后存在更多未失效缓存

不只是五处静默异常：

- `_filter_options_cache` 建立后没有找到任何显式失效调用；新工单、原因、简称、型号变化后最多陈旧
  5 分钟；
- 原因语义缓存 `_sem_cache` 的 key 只有原因 ID。修改原因名称或关键词但 ID 不变时，继续使用旧向量；
- 简称语义缓存 `_alias_sem_cache` 的 key 只有简称 ID。修改简称名称后继续使用旧向量；
- 系列语义缓存 `_series_sem_cache` 也主要依赖 ID，系列名称变化后可能继续使用旧向量。

这会造成“配置页面已经保存，但自动匹配仍按旧配置工作”，比普通 UI 缓存更难察觉。

建议按内容版本而非仅 ID 建 key，或在对应写事务后统一失效。缓存行为必须覆盖
create/update/delete/merge 和产品系列重命名测试。

### P1/P2：全局仓储实例保存请求级可变状态

`services/aftersale/__init__.py` 使用模块级 `_repo = AftersaleRepository()`；`confirm_case()` 又把
`_active_log_ctx` 写在这个共享实例上。

问题：

- 异常路径没有 `finally` 清理 `_active_log_ctx`；
- 下一次请求可能继续向上一次失败请求的日志上下文追加数据；
- 将来开启线程 worker 或增加并发调用时，不同工单会互相覆盖上下文。

请求级日志上下文应作为显式参数传递，或使用 Flask `g`/`contextvars`；至少要在 `finally` 清理。
缓存可以共享，但请求状态不能放在共享 repository 实例上。

### P2：五处静默降级成立，但必须带结构化上下文

`except Exception: pass` 分布在：

- 历史工单向量构建/匹配；
- 原因名语义匹配；
- 产品系列语义匹配；
- 原因—简称亲和度补充；
- 其他语义兜底路径。

“语义失败不阻断主流程”本身可以保留，但降级必须可观测：

- `report_internal_error()` 带阶段名、请求错误编号；
- 指标记录 fallback 次数；
- 不记录完整客户备注等敏感原文；
- 测试要直接触发异常分支并确认仍返回规则匹配结果且日志被调用。

### P2：列表分页可被绕过为无界/异常值

售后 `/pending` 和 `/cases` 直接 `int()` 解析 `page/page_size`，未限制最小值和最大值。调用方可以请求
极大 `page_size`，在 3916 行仓储和多关系序列化路径上放大数据库及内存压力；非法字符串会变成 500。

建议统一为受控解析，`page >= 1`，`1 <= page_size <= 200`，错误输入返回 400。
`/cases/reasons?ids=`、`/alias-affinity` 也应限制 ID 数量。

### P2：管理型写接口权限过宽

以下 `/admin/*` 端点仍只依赖普通 `aftersale:edit`：

- 迁移简称关键词；
- 清理关键词候选；
- 其他批量治理动作。

它们与日常确认工单的风险不同。若继续对业务用户开放，至少应增加二次确认、dry-run 和审计记录；
更稳妥的是增加 `aftersale:admin` 或等价的显式治理权限。

### P3：上帝仓储/组件判断成立

- `backend/database/repository/aftersale/__init__.py`：3916 行；
- `AftersaleProcess.vue`：约 3300 行；
- `AftersaleReasonLib.vue`：约 1900 行。

拆分前先为工单确认/更新、匹配降级、图表口径和原因/简称合并建立 characterization tests。
后端建议依次拆为：

- case repository；
- reason taxonomy repository；
- alias governance repository；
- matching engine；
- analytics repository。

匹配缓存失效和请求上下文应先修，再搬文件，避免把隐患复制到多个模块。

## 5. 数据管理功能归属审查

### 总体结论

当前“数据管理”不应继续作为与产品库、发货、售后并列的一级业务模块。

判断依据：

- 没有独立数据库模型、service、repository 或权限码；
- 路由 `/data-mgmt` 仅要求 `shipping:view`；
- 七项功能全部调用 `/api/shipping/*` 或产品标签接口；
- 每项配置都只影响发货导入、发货解析或发货图表；
- “数据管理”这个名字过宽，容易让用户误以为这里管理全系统数据。

建议保留组件能力，但把导航和信息架构迁入“发货数据”领域。不要为了搬入口而重写已成熟的导入事务。

### 功能归属矩阵

| 当前功能 | 数据所有者/影响 | 推荐位置 | 说明 |
|---|---|---|---|
| 发货清单导入 | 发货原始记录、发货派生表 | 发货数据 → 数据接入 | 明确的发货业务动作 |
| 财务清单导入 | 财务来源发货/销退、财务图表 | 发货数据 → 数据接入 → 财务来源 | 当前没有独立财务模块；以后有财务域再迁移 |
| 操作人分类 | 发货记录，并决定售后待处理队列 | 发货数据 → 数据治理 → 操作人 | 页面必须提示会影响售后待处理数据 |
| 仓库过滤 | 财务销退导入口径 | 发货数据 → 财务来源设置 | 应靠近财务导入，而不是通用配置 |
| 产成品通用件 | 产品组合解析规则 | 发货数据 → 匹配规则 | 当前仅服务发货解析；若未来成为全局产品等效语义，再迁产品库 |
| 标签分析维度 | 发货图表选项 | 发货数据 → 图表设置 | 不属于通用产品标签维护；后端应提供 shipping 专用契约 |
| 外贸客户匹配 | 财务来源内外销、国家/品牌映射 | 发货数据 → 财务来源设置 | 名称建议改为“财务客户分类”，覆盖内销/外贸/非销售四态 |
| 刷新全局数据 | 重建发货派生表 | 发货数据 → 数据健康/高级操作 | 高风险操作，不应常驻一级页头 |

### 推荐页面结构

不建议把所有内容塞进一个巨大 `page-shipping.vue`。可以保持独立子路由和懒加载：

```text
发货数据
├─ 分析看板          /shipping
├─ 订单明细          /shipping/orders
├─ 数据接入          /shipping/imports
├─ 匹配与数据规则    /shipping/rules
└─ 数据健康          /shipping/maintenance
```

旧 `/data-mgmt` 在一个发布周期内重定向到 `/shipping/imports`，再移除首页独立“数据管理”卡片。

### 权限需要随迁移一起修正

当前页面只要求 `shipping:view`，带来多个不一致：

- viewer 能看到导入、重算和保存按钮，通常点击后才收到 403；
- 仓库过滤甚至因后端白名单错误真的可以被 viewer 修改；
- 标签分析维度调用产品编辑接口，拥有 `shipping:edit` 但没有 `product:edit` 的用户仍无法保存；
- 高风险全量重算和日常编辑共用 `shipping:edit`。

短期：

- 前端按 `canEditShipping` 隐藏/禁用所有写按钮；
- 修复仓库权限漏洞；
- 标签维度改为 shipping 专用 service/API，由 `shipping:edit` 授权，不直接借用通用产品编辑接口。

中期可评估细分：

- `shipping:import`
- `shipping:config`
- `shipping:rebuild`

若用户规模小，不必立即增加三种权限；但至少把全量重算从普通查看视角移走，并保留审计记录。

## 6. 与 Claude 汇总的差异

| Claude 结论 | 独立复核 |
|---|---|
| 缓存失效靠人工维护 | 同意，且售后 filter/原因向量/简称向量/系列向量缓存也存在遗漏 |
| 售后五处静默吞异常 | 同意；应保留降级但增加结构化可观测性 |
| 型号删除造成售后未知桶 | 同意，应在产品库统一做引用保护 |
| 售后上帝仓储/组件 | 同意，但缓存和请求状态应先修，拆文件放后 |
| 数据管理整体较成熟 | 导入事务和任务持久化确实成熟；但权限漏洞、任务并发和信息架构不成熟，不能据此低估风险 |
| 导入循环加 `sleep(0)` | 不建议直接作为修复；先做任务互斥与基准压测，`sleep(0)`最多是经验证的辅助措施 |
| 发货值得做项以缓存和重复请求为主 | 排序需上调：仓库越权、重任务并发、取消不完整比前端重复请求更优先 |
| 售后主要是静默异常和大文件 | 还遗漏重复确认非幂等、语义缓存陈旧、共享请求日志上下文和无界分页 |

## 7. 最终实施顺序

### 第 0 批：已知产品分享 XSS

沿用产品库独立审查结论，仍是全系统第一优先级。

### 第 1 批：发货权限与任务准入

1. 修复 `/warehouses/filter` viewer 越权；
2. 为导入/重算建立数据库级互斥租约和 409 契约；
3. 补任务权限、并发和重复提交测试；
4. Claude 同步隐藏 viewer 的写入口。

### 第 2 批：售后正确性

1. 修复重复确认的非幂等计数；
2. 移除共享 `_active_log_ctx` 请求状态；
3. 增加分页/ID 上限；
4. 与产品库共同完成型号删除引用保护。

### 第 3 批：统一缓存失效与异常可观测性

1. 发货产品分析缓存统一失效入口；
2. 售后筛选和语义缓存按内容变化失效；
3. 五处静默降级补错误编号/指标；
4. 对所有缓存建立 mutation → invalidation 测试矩阵。

### 第 4 批：数据管理入口迁移

1. 先修权限，不等待 UI 搬迁；
2. 新建发货子路由并复用现有组件；
3. 标签分析维度改 shipping 专用契约；
4. 保留 `/data-mgmt` 临时重定向；
5. 构建和 Playwright 覆盖权限、导航、导入恢复及配置保存。

### 第 5 批：任务取消、确定性解析与性能

1. 取消令牌贯穿 parsing/inserting/resolving；
2. 订单解析制定稳定 tie-break；
3. 在生产同规格环境压测后再决定 yield/进程隔离；
4. 监控任务时长、RSS、任务冲突和 worker heartbeat。
