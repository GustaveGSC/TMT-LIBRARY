# 产品库模块架构独立审查与优化建议

日期：2026-07-24  
性质：只读审查，无运行时代码变更、无需部署

## 1. 审查范围与验证

本轮没有以 Claude 的结论作为检查入口，而是从产品库的数据模型、路由、服务、仓储和前端调用点向外追踪，覆盖：

- ERP 产品原始数据与 `erp_code_rules`
- 产品分类、成品、产成品、标签、参数、资料库
- 发货解析与发货分析
- 售后分类与售后分析
- 研发成本快照和物料分类
- 产品分享页面

验证：

- `python -m pytest backend/tests -q`：176 项全部通过
- 当前测试集中几乎没有产品规则、产品聚合保存、分类删除和产品导入语义的行为测试；“全绿”不能覆盖本文识别的主要风险。

## 2. 产品库在系统中的真实定位

产品库不是孤立的维护页面，而是多个业务域共同依赖的主数据中心。

| 产品库数据 | 上游/来源 | 下游消费者 | 影响 |
|---|---|---|---|
| `import_product_raw` | ERP 产品导入 | 成品/产成品候选列表、统计、研发成本分类 | ERP 名称或规格修正能否传播 |
| `erp_code_rules` | 产品规则配置 | 产品列表、产品统计、发货分析选项、研发成本物料分类 | 产品边界、隐藏规则、分类结果 |
| `product_finished` | 产品维护 | 发货订单解析、发货分析、生命周期、售后分析分母、成本快照、资料库 | 核心产品主数据 |
| 分类/系列/型号 | 产品维护 | 发货分析、售后原因型号、资料继承 | 删除或移动会跨域改变历史语义 |
| `product_packaged` 与关联表 | ERP 候选+人工关联 | 发货原始明细解析、成本域 | 成品到产成品的解析依据 |
| 产品标签 | 产品维护 | 发货分析维度、资料继承 | 不只是展示标签 |
| 产品资料 | 产品/标签/型号关联 | 登录用户和公开分享页 | 带有公开输出安全边界 |

具体关系：

1. 发货导入会加载 `ProductFinished` 及其 `packaged_list`，把原始发货项解析为 `shipping_order_finished`。
2. 发货图表通过 `ProductFinished -> ProductModel -> ProductSeries -> ProductCategory` 和产品标签生成筛选维度及统计。
3. 售后原因记录直接保存 `ProductModel.id`；售后图表还使用发货完成表和产品分类作为分母及维度。
4. 研发成本导入保存成品编码并可关联 `ProductFinished`；物料分类又单独读取 `erp_code_rules`。
5. 资料可直接关联成品，也可通过产品标签、型号继承；型号或标签变化会改变资料可见范围。

特别需要先明确一条业务语义：禁用 ERP 前缀究竟只表示“不在产品管理界面展示”，还是也表示“不参与发货解析、售后/发货分析和生命周期计算”。当前不同模块的行为不一致，不能在重构时擅自把一个统一过滤器套到所有下游。

## 3. 独立发现的问题

### P0/P1：公开分享页存在输出注入风险

`backend/routes/product/resource.py` 内嵌约 150 行 HTML/JavaScript，但问题不只是文件位置：

- 标题只替换 `<`、`>`，没有完整处理 HTML 属性上下文；
- 外链 URL 被直接放入内联 `<script>`；
- PDF 查看器把文件名、URL 手工插入 JavaScript/HTML；
- `.replace()` 不是上下文安全的转义策略。

资料标题和外链由产品编辑者录入，分享页又是公开页面。恶意内容可能越过当前手工转义形成存储型注入。现有分享安全测试只覆盖签名和部分 OG 输出，没有覆盖 HTML/JS 注入。

建议：

- 使用独立 Jinja 模板并依靠 HTML 自动转义；
- JavaScript 数据只能用 `tojson` 或独立 JSON 数据块传入，避免字符串拼接；
- 外部链接尽量由 Flask 返回重定向，不生成 `location.href="..."` 内联脚本；
- 增加 CSP，并补恶意标题、引号、`</script>`、特殊 URL 的回归测试。

仅把字符串搬进模板文件不足以修复风险。

### P1：ERP 前缀规则存在多套互相矛盾的语义

已确认 `FinishedRepository._get_prefixes()` 未过滤 `is_disabled`，同时影响成品和产成品候选接口。前端再下载全量规则并用 `startsWith` 隐藏禁用成品，因此后端接口本身没有兑现“禁用后隐藏”的边界。

此外还有更深的分裂：

- SQL 使用 `LIKE prefix%`，Python 使用 `startswith`；当规则含 `_`、`%` 或大小写差异时语义不同；
- 产品统计可能把同一编码计入多个匹配规则；
- 研发成本采用“最长有效前缀”；
- 前端与发货选项采用“命中任一禁用前缀就排除”；
- 更新规则时没有拒绝空前缀，空值可能匹配全部编码；
- 重叠前缀没有明确优先级。

建议先对生产规则做只读重叠审计，再确定“最长规则胜出”或“任一禁用规则否决”等业务语义。实现层收敛为共享规则服务，但应提供不同的显式策略接口，而不是一个含糊的万能匹配函数：

- 按类型获取有效候选；
- 判断产品是否可见；
- 按确定优先级分类；
- 生成经过字面量转义、大小写规范一致的 SQL 条件。

即时修复可以先让产品候选接口过滤 `is_disabled=False`，但必须配套行为测试及下游语义确认。

### P1：产品详情保存不是一个事务

`FinishedExpandRow.vue` 的一次“保存”实际依次执行：

1. 保存产品主体；
2. 多次删除/新增产成品关联；
3. 新建、添加、移除标签；
4. 保存参数。

这些请求各自提交。部分产成品和标签请求没有检查 `success`，参数保存失败的返回值也未影响最终结果，最后仍可能提示“保存完成”。

后端保存产品时，分类/系列/型号的 get-or-create 也由多个会自行 `commit()` 的仓储方法组成。中途失败会留下孤立分类或半成品状态。

建议新增“产品详情聚合保存”后端命令接口，在一个数据库事务内处理：

- 产品基础字段；
- 分类/系列/型号解析；
- 产成品 ID 集合；
- 标签 ID 集合；
- 参数。

图片上传涉及对象存储，可继续独立处理；数据库状态必须原子提交。后端契约稳定后，再由 Claude 改前端保存编排。

### P1：型号删除会静默破坏跨模块关联

型号删除目前没有引用保护：

- `ProductFinished.model_id` 会被置空；
- `AftersaleCaseReason.model_id` 会被置空；
- `product_resource_model` 关联会级联删除。

产品编辑者删除一个型号，会同时改变产品分类、售后历史分类和资料继承范围。系统已经做出“不删除成品”的产品决策，型号也不应在存在引用时静默抹除历史关系。

建议优先采用“存在引用则拒绝删除”；如业务需要隐藏旧型号，再增加归档/停用状态，而不是物理删除。

### P1：产品变更后的发货图表缓存失效不完整

`get_chart_options` 缓存包含有效分类/系列/型号和标签维度，但以下变更没有一致地清缓存：

- ERP 规则创建、更新、禁用、删除；
- 产品型号/状态变更；
- 分类、系列、型号移动或重命名；
- 标签创建、删除、改名或移动分类。

结果是产品库已经修改，发货筛选项仍可能保留旧值约五分钟。建议建立一个统一的“产品分析维度已变化”失效入口，由所有相关写操作调用并测试。

### P1/P2：产品原始导入是 insert-only

`ImportProductRepository.bulk_insert()` 先加载全部现有编码，只插入新编码。ERP 后续修正产品名称、规格、分组时，重复导入会被永久跳过，产品候选和研发成本分类继续使用旧数据。

建议改成 UPSERT，并区分 inserted/updated/unchanged；以编码为稳定键，只更新明确允许由 ERP 覆盖的字段，补幂等和纠错重导测试。

### P2：更新接口存在批量赋值和关系校验缺口

分类/系列/型号及 ERP 规则更新使用“请求 JSON 中只要模型有同名属性就赋值”的方式，缺少字段白名单。型号移动时也没有完整验证目标系列和目标范围内的唯一性。

建议：

- route/service 显式列出允许更新字段；
- 验证目标外键存在；
- 移动型号时按目标系列重新做唯一性检查；
- 一致捕获 `IntegrityError`；
- 审计生产数据后，若 `model_code` 确为全局业务唯一，用 Alembic 建数据库唯一约束防并发重复。

### P2：分页和大列表端点缺少上限

产品和产成品候选列表直接 `int()` 解析分页参数，缺少非法值处理及最大 `size` 限制；`/packaged/candidates/all` 无界返回完整候选。资源接口已经有 1..100 的限制，产品接口应统一采用受控分页。

### P2：前端静态参考数据重复请求

每个 `FinishedExpandRow` 实例会重新加载分类树和产成品候选。适合做共享 Pinia 参考数据缓存，要求：

- 首次懒加载；
- in-flight Promise 去重；
- 对应 CRUD 后显式失效；
- 不把产品专属月度数据误当成全局静态数据缓存。

后端落实禁用边界后，前端的禁用前缀过滤可以保留为显示层防御，但不应再决定接口语义。

### P2/P3：组件和边界应继续拆分

`FinishedExpandRow.vue` 当前约 2707 行、102 KB，包含基础信息、分类级联、产成品、标签、参数、资料、发货图表、售后图表等多个独立职责。

建议在聚合保存契约确定后拆为：

- `FinishedCoreForm`
- `FinishedPackagingEditor`
- `FinishedTagEditor`
- `FinishedResourcesSection`
- `FinishedMetricsSection`
- `useShippingMonthlyChart`
- `useAftersaleMonthlyChart`

父组件只维护编辑草稿和协调保存。先补行为护栏，不机械拆成大量微小组件。

### P3：跨模块术语存在碰撞

发货域的 `finished_code` 指解析后的成品；研发成本部分 `finished_code` 又被用于查询 `ProductPackaged`。暂不建议立即改表，但应先补领域词汇表，新代码使用明确名称，例如 `resolved_finished_code`、`erp_packaged_code`，避免继续扩大歧义。

### 小项

- `src/stores/product/packaged.js` 存在展开详情即打印完整关联对象的 `console.log`，应删除。
- 另有产品页面/参数页调试日志，建议一并审查后删除或限制在开发模式。
- 标签删除先提交删除，再单独清理资料的 JSON 条件；第二步失败会留下悬空条件，应合并成事务。

## 4. 与 Claude 报告的对比结论

| Claude 项目 | 独立结论 |
|---|---|
| 禁用前缀语义分裂 | 同意，且实际范围更大：还存在 SQL/Python通配符差异、重叠优先级、空前缀和缓存失效问题 |
| 删除 `console.log` | 同意，可立即由 Claude 处理 |
| 拆 `FinishedExpandRow.vue` | 同意，但应先稳定聚合保存接口和行为测试，否则只是把非原子编排分散到多个文件 |
| 分享 HTML 移到模板/子模块 | 方向不够；应提升为安全修复，模板化必须同时做上下文转义、去内联拼接和安全测试 |
| 缓存分类树/候选列表 | 同意，需 Promise 去重和变更失效，不能只做永久缓存 |
| 后端三层分层已全部落实 | 不完全同意；产品保存的 get-or-create 业务编排仍在 route，仓储自行 commit 阻碍服务级事务 |
| 没发现 N+1 | 本轮检查的主要列表路径未发现明显 N+1，但无界候选、重复加载和跨请求多次保存仍有负载问题 |

## 5. 推荐实施顺序

### 第 1 批：公开分享输出安全（Codex）

- 模板化并消除 HTML/JS 字符串拼接风险；
- 增加恶意输入回归测试；
- 不改变分享 URL 和签名契约。

### 第 2 批：ERP 前缀规则语义（Codex，先审计再改）

- 只读审计生产规则的空值、通配符、大小写和前缀重叠；
- 写清禁用范围及重叠优先级；
- 修复成品/产成品候选后端过滤；
- 统一匹配策略与缓存失效；
- 覆盖列表、total、统计、候选、字面量匹配和重叠规则测试。

### 第 3 批：跨模块数据完整性（Codex）

- 型号删除引用保护或归档；
- 更新字段白名单和关系校验；
- 产品标签删除事务；
- 产品原始数据 UPSERT。

### 第 4 批：产品聚合保存（Codex + Claude 连续联调）

- Codex 先提供原子后端接口、契约和测试；
- Claude 再替换前端多请求保存流程；
- 覆盖任一步失败时数据库完全回滚，以及前端不得误报成功。

### 第 5 批：前端维护性和请求优化（Claude）

- 删除调试日志；
- 共享参考数据缓存；
- 按职责拆分 `FinishedExpandRow.vue`；
- Playwright 覆盖展开、编辑、保存失败、图表和资料选择。

## 6. 实施门禁

每批至少要求：

- 后端：pytest、compileall、git diff --check；
- 数据结构变更：Alembic 单 head、upgrade/check，部署前备份；
- 前端：构建、相关单元/Playwright 测试；
- 产品库变更必须回归发货解析/筛选、售后型号引用、研发成本导入、资料继承；
- 禁止把“禁用规则”直接扩散到发货解析等下游，除非产品语义已经明确，并处理存量与重算策略。
