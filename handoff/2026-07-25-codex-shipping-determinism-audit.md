# B 批：发货解析确定性生产只读审计

## 结论摘要

本批只做代码审查和生产只读统计，没有修改业务数据、解析规则或线上代码。

三类风险的生产结论不同：

1. **同规模成品候选竞争是真实问题。** 同规模候选顺序整体反转时，发货源 726 单、财务源
   720 单解析结果变化。
2. **要求组件/等效件消费顺序当前没有生产命中。** 生产只有 2 组等效件；404 个有组件的成品中，
   没有任何成品的两个要求组件共享可消费的等效件集合。全量订单把要求组件顺序反转后也是 0 差异。
3. **订单元数据取偶然首行是真实且范围更大的问题。** 发货源 2,219 单、财务源 4,546 单至少一个
   元数据字段有多个非空值；绝大多数是同一订单存在多个发货日期。

因此不能把 B 批简化成“补一个 `ORDER BY`”。候选 tie-break 可以按很小回归面稳定下来；元数据口径
必须先由业务确认。

## 审计方式与安全边界

- 审计脚本：`backend/scripts/audit_shipping_determinism.py`。
- 自建 SQLAlchemy 连接，不调用 `create_app()`，避免触发任何应用启动写操作。
- 每轮显式执行 `START TRANSACTION READ ONLY`，脚本只有 `SELECT`。
- 生产执行使用 `nice -n 10/15`；临时脚本只放 `/tmp`，审计后已删除。
- 输出中的订单号、成品编码、产成品编码和元数据值均只保留 SHA-256 前 12 位，不输出原文。
- 聚合统计约 100 秒；全量候选排列模拟每轮约 90 秒。
- 审计结束后 gunicorn 为 active，`/health` 3ms、`/ready` 8ms。

## 一、成品候选竞争

### 生产结构

| 指标 | 数量 |
|---|---:|
| 有组件的成品 | 404 |
| 1 个组件 | 228 |
| 2 个组件 | 159 |
| 3 个组件 | 13 |
| 4 个组件 | 4 |
| 同组件数量候选对（保守上界） | 38,523 |
| 完全相同组件集合的成品组 | 0 |

“完全相同组件集合为 0”不代表没有竞争。不同成品仍可共享部分物料；贪心算法先处理哪个候选，会影响
后续剩余物料。

### 真实订单全量模拟

全量扫描 `shipping_record` 的 133,701 个 shipping 订单和 116,864 个 finance 订单：

| 对比 | shipping | finance |
|---|---:|---:|
| 同规模候选 `finished_code` 升序 vs 降序 | 726 | 720 |
| 当前近似主键顺序 vs `finished_code` 升序 | 1 | 1 |

第一行证明风险可实际改变生产解析结果；第二行说明建议的编码升序规则与当前顺序非常接近，只影响两边
各一单。两条受建议规则影响的脱敏样本：

| source | order hash | 产品种类数 | 当前结果 hash | 编码升序结果 hash |
|---|---|---:|---|---|
| shipping | `2c5216849d0c` | 16 | `a8dbacc5903c` | `8e9ac8205c77` |
| finance | `deef3ae116d2` | 16 | `a8dbacc5903c` | `8e9ac8205c77` |

注意：“当前近似主键顺序”是把生产 `ProductFinished` 的主键顺序显式固定后复现当前稳定排序的结果。
现有 ORM 查询本身没有 `ORDER BY`，所以它不是受数据库契约保证的顺序。

### 建议规则

建议采用：

```text
组件数量降序 → finished_code 升序
```

理由：

- 维持原有“复杂成品优先”的核心语义；
- 编码是唯一、稳定、跨数据库/进程可复现的最终 tie-break；
- 相对当前生产近似行为只有 1+1 单变化；
- 这属于后端确定性规则，不需要前端警告或确认弹窗。

实施前仍应由业务明确接受上述两条订单会发生重算变化；接受后再进入代码实施和全量等价门禁。

## 二、要求组件与等效件顺序

### 生产命中

| 指标 | 数量 |
|---|---:|
| 等效件关系 | 2 |
| 内部要求组件共享等效供给集合的成品 | 0 |
| 全量订单要求组件升序 vs 降序结果差异 | 0 |

因此此前的 `frozenset` 遍历风险在当前生产数据上没有命中。它仍是未来风险：新增等效关系后可能立刻出现，
且 Python hash seed 不保证集合遍历顺序。

### 建议规则

- 构建成品规则时把要求组件保存为排序后的 `tuple`，匹配时禁止直接遍历 `set/frozenset`。
- 保持现有供给消费语义：精确码优先，其余等效码按字典序。
- 新增配置等效件时增加结构测试，覆盖两个要求组件共享同一供给集合的合成场景。

当前生产命中为 0，这项可以作为行为不变的预防性修复，不需要前端展示。

## 三、订单元数据冲突

### 总量

| source | 订单总数 | 任一字段冲突 | 占比 |
|---|---:|---:|---:|
| shipping | 133,701 | 2,219 | 1.66% |
| finance | 116,864 | 4,546 | 3.89% |

### 按字段

| 字段 | shipping | finance |
|---|---:|---:|
| `shipped_date` | 2,076 | 4,533 |
| `operator` | 392 | 0 |
| `channel_name` | 84 | 6 |
| `channel_code` | 91 | 0 |
| `channel_org_name` | 93 | 0 |
| `province` | 89 | 22 |
| `city` | 82 | 23 |
| `district` | 72 | 28 |
| `customer_alias` | 0 | 18 |

代表性脱敏样本：

| order hash | source | 冲突形态 |
|---|---|---|
| `eea8120ac98c` | shipping | 2 个发货日期，其余字段单值 |
| `5baf7450fdca` | shipping | 2 个操作人 |
| `df1582e98b55` | shipping | 2 组省/市/区 |
| `4bfdaaa6144b` | shipping | 3 个发货日期 |

现有 `get_order_products()` 无 `ORDER BY`，第一次遇到的行决定日期、操作人、渠道和地域；
`customer_alias` 则取第一次遇到的非空值。因此：

- 同一数据库在执行计划变化后可能选到不同值；
- 不同字段没有明确业务含义；
- finance 的 18 个客户简称冲突可能把整个订单归到不同客户映射，影响国家/品牌/贸易类型统计。

### 不建议现在直接采用的规则

仅加 `ORDER BY id` 可以固定结果，却只是把“偶然首行”固化成“最早插入行”，没有解释多日期订单应归属哪天、
多地域或多客户订单应归属哪里。不能把技术稳定性冒充业务正确性。

### 建议业务规则

建议业务确认以下口径后再实施：

1. **推荐口径：完成时点。** 将组合后的整单归到最大 `shipped_date`，其余元数据取
   `shipped_date DESC, id DESC` 的同一条代表行，避免不同字段分别取值形成“拼接元数据”。
2. `customer_alias` 若同一 finance 订单出现多个非空值，不应静默任选：
   - 后端继续用同一代表行保证确定性；
   - 导入结果增加“客户简称冲突订单数”，供数据维护页查看；
   - 是否阻断导入需产品决定，当前仅 18 单，建议先告警、不阻断。
3. 若业务认为图表日期应表示“首次发货”，则把第 1 条改为最小日期及
   `shipped_date ASC, id ASC`。需要在“首次发货”和“完成发货”之间明确二选一。
4. 不建议直接按 `(order_no, shipped_date)` 拆单解析；跨日期分批发出的同一成品可能因此无法组合，
   这是另一项业务模型变更。

Claude 复核时应重点判断：客户简称冲突是否需要在导入结果/数据维护页显示。候选 tie-break 和等效件排序
不需要前端感知。

## 四、下一步门禁

在业务确认候选编码升序及元数据日期口径后：

1. Codex 实施稳定候选顺序、要求组件 tuple、代表元数据行规则和合成测试。
2. 至少 3 个不同 `PYTHONHASHSEED` 重复运行，输出 hash 必须一致。
3. 用生产真实 shipping/finance 全量比较新旧结果：
   - 非歧义订单必须 0 不一致；
   - 候选歧义订单单列；
   - 元数据冲突订单按批准口径单列。
4. 两条候选变化订单必须由业务明确接受后才可部署。
5. 本报告没有授权 C 批，也没有开放 resolve-all/resolve-stale 取消。
