## 用户需求原文

> 我发现用正则的方法输入太过于不方便，考虑用与或非的方式输入筛选，然后转化为正则式。
> &：与 |：或 ！非，然后可以用(组合)

---

## 一、一个实现建议：请转成 SQL 布尔条件，而不是转成正则

用户提的是「转化为正则式」。这是实现思路而非需求本身——需求是**输入语法**。
我建议**解析成条件树后直接生成 SQL 的 `AND` / `OR` / `NOT` + `LIKE`**，理由：

1. **AND 与 NOT 在正则里要靠断言**：`a & b` → `(?=.*a)(?=.*b)`，`!a` → `(?!.*a)`。
   MySQL 8 的 ICU 引擎支持断言，但嵌套分组后会生成很难读、很难调试的表达式。
2. **操作数几乎必然含正则元字符**。实测数据里：半角 `(` 出现在 **4,385 条**名称中
   （如「π桌 (V1.1)」），名称里还有 `+`（如「6+25」）、`.`、`*` 等。
   转正则就必须对每个操作数做完整转义，漏一个就是错误结果或语法错误。
3. **SQL 布尔条件每一项都是普通 `LIKE`**，前缀型还能用上索引；
   而 `REGEXP` 必然全表扫描。
4. **报错质量**：自己解析能给出「括号不匹配」「缺少操作数」这类明确提示；
   交给 MySQL 正则引擎只能拿到 ICU 的错误码（我们刚在 3685 上踩过）。

若你有理由坚持走正则，请说明，我这边不需要改动（前端只发 `match_mode=expr`，
不关心服务端如何实现）。

## 二、为什么必须是显式开关（已在前端落实）

**不能自动识别「输入里有 `&|!()` 就当表达式」。** 实测：

| 字符 | 出现在 code | 出现在 name |
|---|---|---|
| `(` | 15 | **4,385**（占 54%） |
| `&` | 0 | 49 |
| `!` | 0 | 16 |
| `|` | 0 | 3 |

自动识别会让「搜 `(V1.1)`」被解析成分组，直接搜坏。
所以前端做成了显式复选框「高级筛选」，不勾选时行为与现在完全一致。

## 三、语法规范

```
expr    := term ( '|' term )*
term    := factor ( '&' factor )*
factor  := '!' factor | '(' expr ')' | operand
operand := quoted | bare
quoted  := '"' 任意字符（不含 '"'） '"'      # 内部全部按字面量处理
bare    := 除 & | ! ( ) " 与首尾空白外的字符序列
```

语义：

- `A & B` — 两个子串都出现（`AND`）
- `A | B` — 任一出现（`OR`）
- `!A` — 不出现（`NOT`）
- `(...)` — 分组，`&` 优先级高于 `|`
- `"..."` — 字面量，用于搜索本身含 `&|!()` 的内容，例如 `"(V1.1)"`
- 操作数两端空白 `strip()`；操作数内部的空格保留（`"桌腿 钢架"` 是一个整体）
- 单个操作数（不含任何运算符）→ 等价于现在的 `LIKE '%值%'`，**行为必须一致**

### 必须处理的错误（都返回 400 + 明确消息，不要 500）

| 输入 | 消息 |
|---|---|
| `(桌腿` / `桌腿)` | 括号不匹配 |
| `桌腿 &` / `& 桌腿` / `A \| \| B` | 缺少操作数 |
| `!` | 缺少操作数 |
| `""` 或纯空白操作数 | 操作数不能为空 |
| 未闭合的 `"` | 引号不匹配 |

### 防御性上限

- 嵌套深度上限 **10**，节点数上限 **50**，超出返回「表达式过于复杂」。
  这是给单 worker 的服务器兜底，避免用户粘贴超长表达式生成巨型 SQL。

## 四、⚠️ 一个既有的隐藏问题，请在本轮一并修

现有三个文本筛选是 `column.like(f'%{value}%')`，**没有转义 LIKE 的通配符**。
所以用户输入 `_` 会被当成「任意单字符」、`%` 被当成「任意串」。

实测影响：物料名称里 `_` 极其常见（`原材料_金属件_铁件_...`），
所以搜 `MJ120_A` 现在会匹配到 `MJ120XA`、`MJ120-A` 等，用户不会预期这个行为。

**修法**：操作数在拼进 `LIKE` 前转义 `\` `%` `_`，并显式指定
`.like(pattern, escape='\\')`。

请在 `expr` 模式与**现有 `like` 模式**下都做转义。`like` 模式的这个改动
严格来说是行为变更，但它修正的是一个用户不会预期的行为，我认为应该修；
如果你担心影响其他调用方，至少 `expr` 模式必须转义，并告诉我 `like` 模式的取舍。

## 五、`match_mode` 取值与 regex 的去留

建议 `match_mode` ∈ `like`（默认）/ `expr`。

**建议同时移除 `regex`**，理由：

- 用户已明确「正则输入太不方便」，前端不再暴露正则开关 → 该取值将无调用方；
- 它还带着一个**未修的缺陷**：非法正则 `[[:nosuch:]]` 返回 MySQL 错误码 **3685**，
  而现有映射只覆盖 `1139` 与 `3690–3699`，因此会变成 **500**
  （我在真实路由上复验过）。移除 regex 这个问题就一并消失，
  不必再去追 ICU 错误码的完整范围。

若你倾向保留 `regex`，那么 3685 必须修（把下界放宽到 3685，或在 regex 模式下
把该次查询的 DBAPIError 一律转 400——正则模式下能让 MySQL 报错的实际只有正则本身）。

顺带：`/api/material/suggest` 因为候选面板已按用户要求移除，
现在也**没有调用方**了，是否保留由你判断。
